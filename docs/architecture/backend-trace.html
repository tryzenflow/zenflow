Zenflow backend trace

A reading order for the NestJS backend and the Python bandit service. Each trail is a path a request or a job takes; each stop is a file and line to open next to this page. Tick stops as you read them (stored in this browser only).

The model in six sentences

  1. One image, several ROLEs

    The API only serves HTTP. Every cron runs once, in the watcher. Queue consumers are separate worker processes.

  2. Nest gathers, Python ranks

    Day loads, preference matrix and bandit state go to POST /v1/place. Python is pure. Nest applies the result and records a SlotProposal.

  3. Degraded, never down

    If Python fails, a frozen TypeScript heuristic places the task and the response says so. A stored TASK always has a start.

  4. Learning is move-or-keep

    A first user move (graded by distance) or a retained session (+1) updates one arm's (A, b) through Python. Nest persists it.

  5. Ingestion is rolling, not bursty

    One ticker claims a few due rows per minute, enqueues jobs, and workers walk the upstream under circuit breakers. The materializer is the only writer.

  6. Row first, fan-out second

    A Notification row is written once. Pub/sub drives live SSE and a queue job drives push. Sweeps repair a dropped fan-out.

Check yourself

Which process fires the 5-minute reminder sweep, and why can an api replica not do it?

The watcher (one replica). ScheduleModule.forRoot() and RemindersWorkerModule are only in jobModules when runsWatcher(role), so the API process has no @Cron providers at all.

  8. 8

    backend/src/scheduler/io/placement-gateway.service.ts:94

  10. 10

    backend/src/scheduler/io/day-load.ts:325

  11. 11

    The wire

    backend/src/scheduler/io/placement-client.service.ts:91

    Kill switch bandit → circuit breaker → attempt (2.5 s) → one fast retry for 502–504 or connect errors inside 300 ms. 4xx is never retried and never counted against the breaker.

  12. 12

    The red path

    backend/src/scheduler/io/python-placer.service.ts:335

    Frozen heuristic via FallbackPlacer; the A/B policy is still rolled and recorded; the response carries schedulingDegraded. Free slot → else up to 30 days late → else last resort pinned by the deadline.

  13. 13

    SlotProposal

    backend/src/experiments/experiment.service.ts:64

    Records what was proposed, by which policy and arm, the feature vector and any degraded reason. Best-effort: a failure here never fails the request. The delayed reward finds it later by sessionId.

  14. 14

    Series variant

    backend/src/sessions/series.service.ts:72

    N real Session rows sharing a seriesId; one A/B event for the whole series. PythonPlacer.placeSeries asks Python for N non-overlapping day-bucket placements.

Check yourself

Python is down and no free slot exists before the deadline. What does the user get?

The pre-flight throws 409 SCHEDULE_INFEASIBLE before any row exists, unless the request already carried an infeasiblePolicy. With a policy the row is inserted and placeSingleDegraded tries up to 30 days late, then the last-resort pin. Either way a stored TASK has a start.

Why is the A/B roll in Nest while all ranking is in Python?

Python is pure (no clock, no RNG, now is a field), so it is deterministic and testable against fixtures. Randomness is data passed in, recorded in SlotProposal, and replayable.

Inside the bandit service

  4. PolicySelector
  5. context_vector

  1. 1

    Entry

    services/bandit/src/api.py:213

    Body size cap, optional bearer token, contract version check (a mismatch is 422 CONTRACT_VERSION, which Nest reports as degraded reason version). The work runs in a threadpool.

  2. 2

    The vocabulary

    services/bandit/src/schemas_place.py:28

    Seven outcomes. NEEDS_INFEASIBLE_CONTEXT is a request for a second call carrying more context; the others are results. The shared TS types in packages/shared must match.

  3. 3

    _Placer

    services/bandit/src/place.py:139

    One request is one placement event: a task or one series. Each member scans its own local-day window, skips days already holding MAX_SERIES_PER_DAY siblings and never overlaps a sibling.

  4. 4

    run()

    services/bandit/src/place.py:596

    Single → one window; series → series_day_windows splits the span into N buckets. Builds one (members × days × FEATURE_DIM) tensor, then runs a plan. A pairwise-sampled series runs two full plans.

  5. 5

    Which pick wins

    services/bandit/src/policies/selector.py:49

    PREFLIGHT is heuristic-only and touches no bandit state. A LINUCB primary applies the LinUCB pick, else falls back to the heuristic. computeBoth runs the other policy for telemetry only.

  6. 6

    Context vector

    services/bandit/src/core/context_vector.py:53

    Seven numbers per candidate day: days to deadline, duration, days from now, weekend sign, fixed-load hours, flexible-load hours, bias. Small on purpose so each arm warms up quickly. The schema.prisma comment that says 22 is stale.

  7. 7

    Slot-first LinUCB scan

    services/bandit/src/core/linucb_best_slot.py:87

    Every free 15-minute start is scored: Σ arm overlap × arm score + wP × preference + wS × stability, ranked across days. LinUCB decides the band; the preference matrix picks the hour inside it and never touches the arm models. Exact ties break by a seeded band order, then distance from band centre.

  8. 8

    score and update

    services/bandit/src/models/linucb.py:46

    θᵀx + α·√(xᵀA⁻¹x) and the rank-one update. /v1/update is a thin wrapper over update for the backend to persist.

  9. 9

    Infeasible handling

    services/bandit/src/place.py:377

    No free slot → EDF displacement of flexible tasks, else the user's chosen fallback (accept conflicts, late, or last resort). core/displacement.py has the algorithms.

  10. 10

    Displacement

    services/bandit/src/core/displacement.py:128

    Cascading EDF repack: moves are returned as data and applied by Nest (DisplacementService, logged as SYSTEM_MOVE).

Check yourself

Which Python files are not on the request path?

core/reward.py and core/sync_conflicts.py (reward is used by preference helpers and the simulator; conflict detection runs in Nest), plus simulation/ and evaluators/.

Learning: move or keep

  1. SessionUpdateService
  2. SchedulingFeedbackService
  3. BanditService
  4. /v1/update
  5. ArmStateRepo.save
  6. Retained cron
  7. Matrix decay
  1. 1

    First move detected

    backend/src/sessions/session-update.service.ts:445

    A drag or resize writes a MOVE SessionEvent with the signed distance. Only the first move of a session (lastMovedAt == null) becomes a reward.

  2. 2

    onFirstMove

    backend/src/scheduler/io/scheduling-feedback.service.ts:54

    Reward is −min(1, |drag| / 240 min). Hands off to the shared path below.

  3. 3

    applyDelayedReward

    backend/src/scheduler/io/scheduling-feedback.service.ts:79

    Finds the LinUCB SlotProposal for the session. No proposal, a heuristic placement, an old feature layout or an old model version all drop the reward. That is the off-policy rule: only the arm that placed it learns.

  4. 4

    Call Python

    backend/src/bandit/bandit.service.ts:42

    POST /v1/update with (arm, x, reward, state); Python returns the new (A, b). 2 s timeout; failure logs and skips, it never breaks the user's edit.

  5. 5

    Persist with a version guard

    backend/src/bandit/bandit-arm-state.repository.ts:42

    Optimistic compare-and-set on version. Losing a race is accepted and logged; the row is created lazily at the ridge prior.

  6. 6

    Python side

    services/bandit/src/api.py:253

    Hydrates the arm (cold = ridge prior), applies the update, returns matrices. No state is kept in the service.

  7. 7

    The keep signal

    backend/src/scheduler/io/retained-sessions.service.ts:70

    Every 30 minutes (watcher): a user-created TASK whose end plus a grace period has passed and that was never moved becomes RETAINED (+1). retainedAt makes a re-run a no-op. Also reinforces the preference matrix.

  8. 8

    Nightly decay

    backend/src/scheduler/io/matrix-decay.service.ts:49

    03:00: every user's 168-cell matrix decays with a 21-day half-life, under a row lock so it cannot lose a race with a reinforcement write.

  9. 9

    Partition upkeep

    backend/src/scheduler/io/session-event-partition.service.ts:28

    02:10 UTC: pre-create current plus two future monthly SessionEvent partitions, drop those older than 12 months. An insert into a month with no partition would fail, hence the metric.

Check yourself

A student drags a task that was placed by the heuristic arm. Does LinUCB learn from it?

No. applyDelayedReward finds no LinUCB proposal (or the arm is null) and counts no_proposal. The preference matrix is reinforced regardless of which policy placed it.

Ingestion: tick → fetch → materialize

How a student's timetable, exams and Moodle deadlines reach their calendar without a daily burst.

  1. Ticker (1 min)
  2. claimDue (CAS)
  3. portal-fetch / lms-fetch
  4. FetchProcessor
  5. IngestionFetchService
  6. watcher
  7. parser
  8. Materializer
  9. Notification
  1. 1

    The heartbeat

    backend/src/ingestion/ingestion-ticker.service.ts:150

    The only scheduled trigger. Read the class comment for why it replaced three crons. The cadence lives in each row's nextDueAt, not in the cron expression.

  2. 2

    tick()

    backend/src/ingestion/ingestion-ticker.service.ts:169

    Kill switch before any claim (claiming then skipping would silently push every student a period out). Per kind in order: breaker peek, batch size, queue backlog check, claimDue, enqueue. First enqueue failure hands every remaining claim back and stops.

  3. 3

    The claim

    backend/src/ingestion/ingestion-schedule.service.ts:263

    Read the most overdue rows, then updateMany with nextDueAt still equal to what was read. A competing tick matches nothing. The claim moves nextDueAt a full period out immediately.

  4. 4

    Spreading the load

    backend/src/ingestion/core/schedule-plan.ts:109

    ceil(population / ticksPerPeriod) clamped to [1, INGESTION_TICK_MAX_BATCH]. nextDueAfterRun measures from now, not from the old due time, so seeded rows drift apart and stay spread. There is no jitter on purpose (core is pure).

  5. 5

    Consumer registration

    backend/src/ingestion/fetch.processor.ts:33

    Concurrency 1 per replica and a default limiter of one job start per INGESTION_REQUEST_DELAY_MS across replicas. onFinalFailure is the stalled-job hook.

  6. 6

    handle()

    backend/src/ingestion/ingestion-fetch.service.ts:78

    Kill switch (park 60 s, no attempt used), then execute. An open breaker parks the job for the breaker's remaining time. Any other error records the exhaustion on the last attempt and rethrows for BullMQ backoff.

  7. 7

    execute()

    backend/src/ingestion/ingestion-fetch.service.ts:114

    Peek the upstream breaker (no login while open), dispatch by kind, then recordOutcome. A walk cut short by the breaker keeps its writes but is neither success nor a student failure.

  8. 8

    A full pass

    backend/src/ingestion/timetable-watcher.service.ts:124

    Gate on discovery for the term (run it inline if missing), maybe serve from cache, sign in, fetch week by week with a politeness delay, parse, materialize, reconcile deletions only if every week came back, flush the digest, record into the shared cache.

  9. 9

    Discovery

    backend/src/ingestion/enrollment-discovery.service.ts:101

    DKHP registration history, once per term: keep sections whose latest event is a registration. It never narrows the confirmed set on failure.

  10. 10

    Pure parsing

    backend/src/ingestion/core/parse-portal.ts:167

    Upstream JSON → ParsedBlock[] with a stable externalKey. No Prisma, no Nest, no clock: easy to test with the DLU fixtures.

  11. 11

    The breaker seam

    backend/src/portal/portal-api.service.ts:306

    Every request goes through one breakers.run("dlu-portal", …). 5 consecutive timeouts, connection errors, 5xx or 429 open it; 4xx and parse errors never count.

  12. 12

    The single writer

    backend/src/ingestion/materializer.service.ts:176

    Per block: look up [userId, externalKey]. Deleted by the student → skip. New → create. Same → unchanged. Moved by the student → keep their time. Otherwise apply upstream, with no SessionEvent (it must not feed the reward).

  13. 13

    Removals

    backend/src/ingestion/materializer.service.ts:252

    Keys not seen in the run's forward window are soft-deleted on the first miss. Callers must skip this when any fetch in the run failed.

  14. 14

    Digest → notifications

    backend/src/ingestion/materializer.service.ts:564

    One notification per item type per run, then one sync-conflict check per (source, type). A worker killed between the walk and this point loses that pass's notifications; the calendar stays correct.

  15. 15

    Conflicts

    backend/src/ingestion/sync-conflicts.service.ts:46

    Compares freshly written fixed rows with the student's own TASKs; raises one sync_conflict.* notification per distinct overlap set. "Reschedule them all" is ConflictRescheduleService.

  16. 16

    Optional: cross-student cache

    backend/src/ingestion/occurrence-fanout.service.ts:91

    Off by default. Recording is always on (it costs nothing); fan-out writes classmates' sessions only when the flag is on and two different students saw the same transition.

Check yourself

Why does the claim move nextDueAt before the job runs, and what repairs a lost job?

At-most-once: a second tick or replica cannot claim the same row. If enqueue fails the claim is handed back; if the job stalls, onFinalFailure releases it with a compare-and-set on lastClaimedAt.

A student moves a lecture, then the university changes its room. What happens?

The materializer sees lastMovedAt, counts it as skippedMoved and keeps the student's time. If the university cancels the lecture it is still soft-deleted.

Check yourself

The API waits 25 s and gives up. Is the sync cancelled?

No. The job is independent of the request; bookkeeping (deferral on success, failure count) is done by the job, and the client gets 202 syncPending.

  1. 1

    backend/src/notifications/notifications.service.ts:283

    Written once by the materializer, the conflict detector or a reminder. For ingest events it can also create a calendar Session. Localised for the recipient.

  2. 2

    Publishes to pub/sub and enqueues one push job per provider (push_{id}_{provider}), each retried briefly. A dropped enqueue is counted and repaired by reconcileRecent. notify() is the fire-and-forget wrapper.

  3. 3

    backend/src/notifications/notification-pubsub.service.ts:102

    At-most-once, 250 ms timeout, never throws; on failure it emits locally. Clients dedupe by notification id and the inbox endpoint is the source of truth after a reconnect.

  4. 4

    Subscribe

    backend/src/notifications/notification-pubsub.service.ts:83

    Only HTTP roles subscribe. Each re-emits into the local emitter, so a row raised by any worker reaches the client's own connection.

  5. 5

    SSE endpoint

    backend/src/notifications/notifications.controller.ts:39

    Filters the emitter by userId and maps to a DTO. A gauge counts open connections.

  6. 6

    The consumer

    backend/src/notifications/notify.processor.ts:37

    Kill switch → drop the job (no retry). push runs under the per-provider breaker so an open FCM/APNs parks only that provider's job. reminder calls fire().

  7. 7

    Delivery

    backend/src/devices/push.service.ts:74

    Loads the row (throws if missing so the retry finds it after commit), respects allowNotifications, sends to the user's devices and prunes tokens the provider reports dead.

  8. 8

    Sweep (watcher)

    backend/src/reminders/reminder-sweep.service.ts:28

    At boot and every 5 minutes: arm reminders firing within 24 h and run reconcileRecent. This is the only place reminders get armed.

  9. 9

    Arming

    backend/src/reminders/reminder-scheduler.service.ts:154

    One delayed job per reminder occurrence, id reminder_{id}_{startMs}, with 5–10 s jitter so push bursts spread. Arming twice is a no-op. Nothing is cancelled.

  10. 10

    Firing

    backend/src/reminders/reminder-scheduler.service.ts:190

    Re-reads the DB: deleted, moved or past → drop (a moved session is re-armed for its new start). Claims firedForStart and creates the Notification in one transaction, so a retry cannot double-send.

  11. 11

    The repair loop

    backend/src/notifications/notifications.service.ts:239

    Rows 1 minute to 2 hours old with no push job get one. Job ids are deterministic, so an existing job in any state is left alone.

Check yourself

Redis pub/sub is down. Does the user still get the notification?

The row is in Postgres, so the inbox shows it. The publish falls back to a local emit (same-process listeners only). Push is independent: it goes through the queue.

A session is moved after its reminder job was armed. What fires?

The old job runs, fire() sees the plan's start differs from armedStart, arms the new start and sends nothing.

Check yourself

Redis is unreachable for a minute. What is lost?

Nothing already enqueued (AOF). An enqueue that fails or times out is lost for that call; the ticker hands claims back, the reminder sweep and reconcileRecent re-derive on the next run. A one-off push enqueue that failed past the 2-hour reconcile window is dropped.

Footguns

  • Ranking never goes in Nest (ADR-0003). The frozen TS fallback changes only for bug fixes, and then golden:export and test_golden_ts.py must stay green.
  • Any new placement path must go through placeOrDiscard, or a failure leaves a TASK with a null start.
  • The ticker’s claim moves nextDueAt before the job runs. A lost job is not retried until its claim is released or the next period arrives.
  • Circuit breaker state is per process. Reasoning about "the" breaker across replicas is a bug.
  • SSE is at-most-once. Clients dedupe by notification id; the inbox endpoint is the source of truth.
  • A pass can lose its notifications if the worker dies between the walk and flushDigest. The calendar is correct; the notification is gone.
  • Session.deleted is a soft delete. Every read filters it except the materializer’s idempotency lookup, which must see deleted rows.
  • PLACEMENT_CONTRACT_VERSION lives in packages/shared and in Python. Bump both; a mismatch degrades every placement with reason version.
  • Durations are positive multiples of 15 minutes and the grid is 15 minutes. DLU wall-clock strings are in DLU_TZ, not the student’s timezone.

Docs vs code

Found while tracing. The code is what these trails describe.

  • Confirm/miss gate. docs/backend/ingestion.md and docs/backend/data-model.md describe a two-run confirm/miss gate using Session.syncConfirmedAt / syncMissedAt. In code, materialize() makes a new item visible on first sight and reconcileDeleted() soft-deletes on the first miss. Only the schema, one migration and spec fixtures mention the columns.
  • Reminders. docs/backend/scheduler.md and data-model.md describe in-memory SchedulerRegistry timers re-armed through syncUser() on every mutation. In code reminders are BullMQ delayed jobs on notify. The API only stores SessionReminder rows; the watcher’s 5-minute sweep arms them, so a new or moved reminder can be armed up to 5 minutes late.
  • SessionEvent types. data-model.md lists a RESIZE event type. The enum is CREATE, MOVE, RETAINED, SYSTEM_MOVE.
  • Feature dimension. The BanditArmState comment in schema.prisma says d = 22. FEATURE_DIM is 7 since the ADR-0001 amendment.
  • redis-cache. ADR-0017 says redis-cache was added. There is no such service in the compose files and no client in the code; CACHE_URL is the session Redis.

Not covered here: auth (OTP and Redis sessions), files and signed URLs, devices CRUD, tags, mail, the credential envelope encryption, observability internals, and deploy (see docs/ops/).
