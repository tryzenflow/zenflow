# Zenflow Heuristic Algorithm

Zenflow uses Earliest-Deadline First (EDF) to help schedule tasks by prioritizing the deadlines.

The user provides:

- Task name
- Estimated duration (must be multiple of 15 mins)
- Earliest date to perform the task
- Deadline (latest date by which the task needs to be completed)
- Tags (optional)
- View (current day / week / month)

Underlying attributes:

- Work hours (default is 9-17 converted to minutes as 540-1020)

Then, depending on the view, the slots will be determined. For example, in the week view:

- The options are 15-minute slots
- The start `s` is 9am Monday, end `e` is 5pm Friday
- Task earliest start is `ts = max(s, ts)` , end is `te = min(deadline, e)`
- Task deadline needs to satisfy `s <= deadline <= e`

EDF will:

- Schedule early for tasks with tight deadlines (in order), which is O(1)

# Intelligence Layer

The schedule generated by EDF is basic and not personalized. The user will manually adjust the schedule, we track every manual edits done by the user, which can be used to train an ML model and personalize their behavior.

## Actions Tracked

- Resize tasks → estimated duration differs from what they initially planned
- Move tasks away from the suggested slot → dislike doing them at time interval X-Y, prefer time interval X’-Y’ instead

# Evolution

---

## Phase 1: The Deterministic MVP (Core Utility)

**Goal:** Build the foundational CRUD application and the core EDF scheduling engine with elegant multi-tag structural rendering. No intelligence yet—just strict, deterministic logic.

### Technical Focus

- **Frontend/Backend:** Setup the NestJS API and React PWA. Build the main calendar UI (day/week/month views).
- **Multi-Tag UI Layout:** To preserve hyper-constrained grid space on the timeline canvas, the UI implements an intelligent overflow pattern. Cards render the highest-priority tag fully (`#backend`), while wrapping additional tags into a compact counter chip (`+2`). The full tag drawer is exposed on card click or hover.
- **The Engine:** Implement a pure Earliest-Deadline First (EDF) algorithm. When a user adds a task, the system sorts it strictly by deadline and drops it into the first available 15-minute slot within their specified working hours (e.g., $9 \rightarrow 17$).
- **Data Foundation:** Implement the `task_events` audit table in PostgreSQL. To support native multi-tag flexibility without joining overhead at the MVP stage, tasks store tags as a native PostgreSQL text array (`tags: String[]` via Prisma). Telemetry tracking begins on day one, recording how users interact with, move, or resize multi-tagged tasks.

---

## Phase 2: Heuristic & Rule-Based Adaptation

**Goal:** Introduce immediate personalization using hardcoded statistical rules, rolling averages, and compounding tag calculations to make the engine feel inherently "smart" with zero machine learning overhead.

### Technical Focus

- **Multi-Tag Duration Correction (Bias Blending):** Write a daily background cron job in NestJS that calculates a user’s historical "estimation bias" *per tag*. Because a single task can have multiple tags (e.g., `#admin` and `#finance`), the engine resolves conflicting multipliers using a **Conservative Max-Bias Strategy**:
    - If `#admin` tasks historically run over by $1.5\times$ and `#finance` tasks run over by $1.1\times$, a task carrying both tags is scaled by the higher modifier ($1.5\times$) before feeding into the EDF engine, preventing tasks from compounding exponentially while protecting the user's schedule.
- **Static Penalty Matrix:** Build a 7x48 matrix (7 days, forty-eight 30-minute blocks) per user. Every time a user drags a task out of a slot, the system increments that specific slot's penalty score.
- **Tag-Inherited Constraints:** When the EDF engine evaluates optimal placement, a task with multiple tags inherits the *strictest* historical penalty rules associated with any single tag in its array, aggressively routing the task away from high-aversion time blocks (such as preventing a `#finance` task from dropping into a Friday afternoon slot).

---

## Phase 3: Contextual Bandits

**Goal:** Transition from rigid heuristic rules to an algorithmic framework that balances exploring new schedule distributions with exploiting known user habits in real-time.

### Technical Focus

- **The Framework:** Implement a Contextual Bandit algorithm (such as LinUCB) running inside a lightweight Python microservice (built with FastAPI) alongside your NestJS backend on the VPS.
- **Multi-Hot Feature Vectorization (Context):** Linear bandit models cannot read an array of text strings natively. The FastAPI service processes tags by flattening them into a fixed-width **Multi-Hot Encoded Vector**.
    - If the system recognizes a global pool of 6 tags, a task with two tags is transformed into an explicit binary array (e.g., `[1, 0, 1, 0, 0, 0]`).
    - The complete feature vector is assembled dynamically:

        $\text{Context Vector} = [\text{day\_of\_week}, \text{hours\_to\_deadline}, t_1, t_2, \dots, t_n, \text{current\_day\_load}]$

- **The Loop:**
    1. NestJS flattens the multi-tag context and passes the vector to the Bandit service.
    2. The Bandit service scores the available time slots (arms) based on tag weights and returns the highest-reward slot.
    3. The user either accepts it (high reward) or overrides the system by dragging it elsewhere (negative reward), updating the model weights in real-time.

---

## Phase 4: Collaborative Archetypes & Cold Start

**Goal:** Eliminate the initial data-void for new users by leveraging aggregate behavioral signatures across your entire user base using a Recommender System framework.

### Technical Focus

- **Clustering & Multi-Tag Matrix Factorization:** Run periodic matrix factorization (using LightFM or collaborative filtering techniques) on your global database. Instead of analyzing tags in isolation, the engine analyzes **Tag Co-occurrence Matrices** to observe how users cluster cross-functional work.
- **User Archetypes:** Identify complex behavioral profiles based on multi-tag signatures (e.g., pairing `#dev` + `#ops` maps to "The Night Owl Developer", while pairing `#marketing` + `#copy` maps to "The Creative Lead").
- **Solving the Cold Start:** When a new user completes their brief onboarding survey, Zenflow maps their self-selected role directly to a behavioral cluster. Instead of starting from scratch, the system seeds their initial Multi-Hot Bandit weights and Penalty Matrix with the baseline averages of their matching multi-tag archetype.

## Roadmap Summary

| **Phase** | **Core Scheduling Mechanism** | **Complexity** | **Data Required** |
| --- | --- | --- | --- |
| **Phase 1** | Pure Heuristic (EDF Sorting) | Low | None (Baseline) |
| **Phase 2** | Modified EDF + Rolling Averages / Rules | Medium-Low | ~1-2 weeks of single-user history |
| **Phase 3** | Contextual Bandits (LinUCB / Policy) | Medium-High | ~1 month of single-user history |
| **Phase 4** | Bandits + Collaborative Filtering (RecSys) | High | Multi-user dataset (Aggregate data) |
