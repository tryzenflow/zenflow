# DLU fixtures

Synthetic data for 150 test students across 9 departments, standing in for
the real LMS + student portal. No real names/ids/course content —
generic placeholders shaped to match the real response shapes (`lmsfetchall.md` at repo root).

Generated by `generate.js` (deterministic, seeded). Edit `generate.js` and
re-run `node generate.js` rather than hand-editing the JSON, except for
one-off creation/change/deletion tests (see below).

| File                        | Mirrors                                                       | Keyed by                                |
| --------------------------- | ------------------------------------------------------------- | --------------------------------------- |
| `students.json`             | — (login + profile fixture)                                   | array                                   |
| `lms-courses.json`          | Moodle course catalog (current term)                          | array, `id`                             |
| `lms-enrollments.json`      | `core_course_get_enrolled_courses_by_timeline_classification` | `studentId -> course id[]`              |
| `lms-events.json`           | `core_calendar_get_calendar_monthly_view` events              | events by course id + `enrolledCourses` |
| `portal-sections.json`      | class-section catalog (internal, not a real endpoint)         | `{ sections: [...] }`                   |
| `portal-timetable.json`     | `GET /api/student/DrawingStudentSchedules`                    | `studentId -> row[]`, one ISO week      |
| `portal-exams.json`         | `GET /api/student/exam`                                       | `studentId -> row[]`                    |
| `portal-regist-history.json` | `POST /api/student/getAllRegistHistory` (DKHP)               | `studentId -> event[]`, every term      |
| `portal-year-term.json`     | `GET /api/student/yearandterm`                                | static                                  |

## Coverage

- **9 departments** (IT, Economics, Tourism, Business, Chemistry, Biology,
  Social Studies, English, Linguistics), each with its own program id and 6
  core subjects (`101`/`102` → `201`/`202` → `301`/`302`).
- **Optional subjects**: 4-item general-elective pool (`GEN-EL1..4`), not
  department-scoped — shared sections across departments.
- **Retaking a failed subject**: ~1 in 7 students fail their `201` course.
  Half retake and pass later (`retakeStatus: "resolved"`), half retake right
  now (`"in-progress"`). Same `CurriculumID`, new `ScheduleStudyUnitID`.
- **Dual study programs**: ~10% of students carry a `SecondaryStudyProgramID`
  (`students.json`) + an extra course from that programme in their load.
- **Registration history (DKHP)**: an event log per student. The current
  term's latest-registered sections equal the timetable's sections. Every 5th
  student re-registers a section (register, cancel, register), every 7th
  registered then cancelled a section they do not attend, every 3rd has an
  event in the previous term (served only when that term is asked for).
- **Groups vs. classes**: each department splits into 2 classes
  (`TESTCLASS-{DEPT}-A`/`-B`); each core subject runs 2-3 parallel groups per
  term, chosen independently of class — so both "same class, different
  group" and "different class, same group" occur. Example: `TESTCUR-IT-302`.
- **Shared sections (issue #56)**: `portal-sections.json` sections carry a
  `students` array — department cores ~9–12 students, electives up to ~19,
  retake/secondary sections 1–3.

## Simulating creation / change / deletion

Static snapshots. New = add a row/event. Change = edit room/period/time/grade.
Delete = remove a row/event. `WeekScheduleID` / `Examination` / Moodle
`instance` are the ids move/delete detection keys on
(`parse-portal.ts`/`parse-lms.ts`) — keep stable for "same activity, new
details", mint new only for a genuinely new activity.

`fake-dlu-server.ts` serves this fixture set (via `fake-dlu-fixtures.ts`)
whenever the files are present, so editing them is how to simulate a change.
Neither upstream's data request names a student, so the fake bakes the
`StudentID` into what login returns — the portal token
(`fake-portal-token-<StudentID>`) and the Moodle cookie
(`MoodleSession=auth-<StudentID>`). The timetable fixture is one reference
week; any other week of the same term is served as that week shifted, with
per-week `WeekScheduleID`s. An unknown username falls back to the ad-hoc
generator. The discovery endpoints (`getAllRegistHistory` on the DKHP side,
enrolled courses paged 2 at a time) are served too.

DKHP shares the login path with the portal, so the fake tells them apart by
`clientid`: `dtl` is DKHP and must carry a non-empty `apikey` (`DKHP_API_KEY`
in `.env.dev`; start the fake with `FAKE_DKHP_API_KEY` to require an exact
value). Counter keys are `dkhp:authenticate` and
`dkhp:history:<year>:<term>:<studentId>`. Set `FAKE_DLU_LATENCY_MS` to delay
every upstream response so wall-clock time means something in a benchmark.

## Baseline: sync repetition without caching (pre issue #56)

Seeded all 150 students as real accounts (`seed-and-sync.js`, OTP via
Mailpit), connected LMS+PORTAL, set the 3 watcher crons to `EVERY_MINUTE` for
5 minutes, measured via `fake-dlu-server.ts`'s `/_/stats` counter (keyed by
actual resource, not raw URL).

|                                               |                                  |
| --------------------------------------------- | -------------------------------- |
| Total upstream requests (5 ticks × 150 users) | **6,395**                        |
| Distinct resources requested                  | **21**                           |
| Redundancy ratio                              | **~305×**                        |
| Data endpoints (calendar/timetable/exam)      | 3,399 req / 17 resources (~200×) |
| Auth endpoints (login/sesskey/authenticate)   | 2,996 req                        |

All 21 resources are term-scoped, not student-scoped, and uncached today —
the number issue #56 should collapse toward ~21. Re-run after that lands and
diff.

## After issue #56: cache + fanout benchmark (2026-10-02)

`scripts/fixtures/dlu/bench.sh` runs it end to end; method, results and
limitations are in `docs/benchmarks/ingestion-cache-benchmark.md`. In short: 150
students, 1-minute ticks, 5 ticks per run on a 2-minute period (75 students per
tick), with student moves and deletes injected and then upstream room changes and
removals. No cache (A) against cache + fanout (B): the cache cuts total requests
by 49% and data requests by 54%, calendars are identical, and students' own moves
and deletes are preserved. `bench.sh` is destructive to the dev database and needs
the dev docker stack and a built backend.
