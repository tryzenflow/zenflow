Verdict

Both AFTER builds are much faster than BEFORE on this workload, and AFTER-python is faster than AFTER-legacy on almost everything, with one nuance for large series. The differences are far larger than the pass-to-pass spread (whiskers).

  • Medium load, 10 VUs (standard mix), median of 3 passes: p95 A 13.2 s, B 1.16 s, C 0.46 s; p50 A 373 ms, B 141 ms, C 79 ms; throughput A 2.8, B 33.7, C 70.5 req/s. At 1 VU p95 is 1.69 s / 251 ms / 106 ms.
  • BEFORE does not scale: one task placement with a 30 or 60-day scan costs ~12 s / ~24 s p50 on BEFORE versus ~0.32 s (B) and ~0.15 s (C). At 25 VUs A's p95 is 35 s; at 50 VUs it hits the 60 s client timeout (22% errors at medium, 50% at light). B and C stay at 0% errors at every scale. A is a single saturated Node event loop (~120% CPU); B and C use the full 2 CPUs (~196%), so B and C are CPU-bound at 2 cores.
  • Python vs legacy (C vs B): p95 at 50 VUs 2.4 s vs 5.6 s; throughput 67 vs 33 req/s; DB statements per request 38 vs 47 (BEFORE 105-144). The bandit container adds ~35-40% of one core at this load.
  • Large series: post_series p50 is lower on C than B at every size (8 sittings 497 vs 1109 ms, 12: 899 vs 1575 ms, 20: 1695 vs 2702 ms), but in the 12x and 20x cells C leaves the API at 115-129% CPU (B: ~190%), i.e. C is latency-bound on the sequential Python call(s), not CPU-bound, and its whole-iteration p50 in those cells is higher than B (713 vs 318 ms at 12x, 1378 vs 650 ms at 20x, because the cell is dominated by the series request). Gains for large series are therefore smaller and less clear than for single tasks.
  • Fixed-load level (light 8 / medium 25 / heavy 61 per week) barely matters for B and C (p95 at 10 VUs within ~10%); the scan window and series size matter far more.
  • Open model (arrival 1-8 it/s): C sustains it with 0 dropped iterations (p95 123 ms); B drops ~13 iterations; A drops 164 and times out.
  • Infeasible path (separate): AFTER answers 409 SCHEDULE_INFEASIBLE in 43 ms (B) / 74 ms (C), then accepts a policy (late placement) in ~190 ms (B) / ~210 ms (C). BEFORE returns 400 "No open slot" (29 ms) and rejects the policy retries (400, unknown field). Displacement was not exercised.
  • Integration bug that changes the picture in production: python mode silently degrades for every user whose preference matrix is empty (all cold-start users); see Integration findings. These results use pre-populated matrices.

Caveats: A's high percentiles at 25/50 VUs are censored by the 60 s client timeout and rest on few completed iterations; 4 A attempts were invalidated because its backlog did not drain and were rerun. The steady state is one sample per variant. LinUCB state is cold (no learned bandit state), so LinUCB-primary paths are exercised only trivially. One machine, one user per VU, synthetic schedules: do not extrapolate absolute numbers to production hardware.

Integration findings

  1. Cold-start users are never served by Python (bug, not fixed). A new user has preferenceMatrix = [] until something learns it. The TS paths normalise a wrong-length matrix to zeros, but PlacementGateway.buildRequest sends user.preferenceMatrix as is and the Python schema (schemas_place.py) requires exactly 168 entries, so POST /v1/place answers 422 "preferenceMatrix must have 168 entries". Nest logs it at error level and falls back: the response carries schedulingDegraded: true and the SlotProposal row is TS_FALLBACK / http_4xx; an infeasible request returns 503 SCHEDULER_DEGRADED although the Python service is healthy. Reproduced with tools/smoke.js C --cold. Likely one-line fix: send a zero-filled 168-array when the length is wrong (same normalisation as UsersService.getPreferenceMatrix). The load test works around it by seeding an identical 168-entry matrix for every user. Unverified hypothesis: since 422 is a hard failure, one cold user placing repeatedly could trip the per-process breaker (5 consecutive failures, 15 s open) for everyone.
  2. Smoke test with a populated matrix (python mode): single task and 8-sitting series placed by Python (PYTHON/-); the infeasible case returns 409 SCHEDULE_INFEASIBLE with options; ACCEPT_LATE_DEADLINE returns late: true; ACCEPT_CONFLICTS is accepted; displacement was not triggered. With the bandit container stopped: tasks and series place with schedulingDegraded: true (the first requests wait the 2.5 s timeout, then breaker_open), infeasible requests return 503 SCHEDULER_DEGRADED with or without a policy (as ADR-0003 2.4 specifies). After restarting the container the breaker closed about 15 s later and placements returned to Python. No functional bug found in that path.
  3. Shadow mode (legacy answers, Python compared; 20 smoke tasks plus a 30 s, 10-VU task workload): 348 /v1/place calls, all 200, 0 "shadow mismatch" and 0 "shadow ... failed" log lines. Shadow only covers single tasks, and LinUCB comparisons are trivial with cold bandit state.
  4. Minor: Server-Timing phases exist only on the Python placement path (B and BEFORE emit none), so per-phase attribution is only available for C; db_apply is absent for series in C.
